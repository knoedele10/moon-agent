# 需求分析：自媒体博主「稿件 · 素材 · 发布」数据库

> 状态：数据层已落地（见 §12）；排期自动导出任务已落地（见 §13）　日期：2026-10-21 / 2026-10-24
> 目标仓：`E:\blog-my`（Moon Agent）　前置约定：不改现有表语义、不做破坏性迁移

## 1. 背景与问题

现在的 Moon Agent 有对话、技能、知识库、记忆、团队任务，但**没有「内容生产」这一层**：
博主从「灵感」到「成稿」到「多平台发布」的过程散落在聊天记录、桌面文件夹与各平台后台里。

四个具体痛点：

1. **素材找不到、用完就丢**：图片/视频/口播片段/金句/链接没有统一登记，复用时靠翻文件夹；
2. **一稿多版无法管理**：同一篇稿子要改成长文、短图文、视频脚本，正文各写一份，改一处漏三处；
3. **发布状态靠脑子记**：哪个平台发了、哪天排的、发失败了、数据如何，没有一条可查的记录；
4. **Agent 帮不上忙**：模型不知道有哪些素材可用、某篇稿子改到哪一步，只能每次重新问。

## 2. 目标与非目标

**目标（做完要能回答的问题）**

- 我手上还有哪些素材没用过？这条素材被哪几篇稿子引用过？
- 这篇稿子现在到哪一步了？谁最后改的？改了哪些内容？
- 本周该发什么、哪个平台还欠一篇、上次发布失败了要不要重试？
- Agent 能否直接检索素材/稿件、按指令改稿、登记发布，而不越权？

**非目标（本期明确不做）**

- 不做真实的多平台自动发帖（各平台无公开写接口/有风控）；只做**发布台账**与「一键复制/导出」；
- 不做图片/视频转码、不做 CDN；素材只登记元信息 + 本地/对象存储键；
- 不做复杂审批流（先做单人 + 可选复核标记）；
- 不做数据大盘可视化（先出接口，界面后置）；
- 不碰现有 `User / Conversation / KBDocument / AgentSkill` 等表的语义。

## 3. 角色与场景

| 角色 | 诉求 | 权限 |
| --- | --- | --- |
| 博主本人（Owner） | 全流程管理 | 全部读写 + 删除 + 发布登记 |
| 助理/编辑（可选，后置） | 改稿、传素材，不能删与发布 | 读写稿件与素材，只读发布记录 |
| Agent（模型侧） | 检索、改稿、登记发布 | 按工具白名单，写操作走确认 |
| 只读访客 | 无 | 不开放 |

**核心场景**

1. 灵感来了：新建「选题」→ 挂 2 条素材 → 出初稿；
2. 写长文：正文 Markdown → 派生「公众号版 / 小红书版 / 视频脚本版」，共享同一份素材引用；
3. 排期：定稿 → 指定平台与时间 → 到期提醒 → 发布后回填链接与数据；
4. 复盘：按平台/标签看产出与效果，找出复用率最高的素材；
5. Agent：用户说「把上周那篇关于 RAG 的稿子改短一点，明天发公众号」→ 检索→改版本→建排期→等确认。

## 5. 数据模型草案（新表 5 张，全部带 user_id）

```
content_asset            素材
  id, user_id, kind(enum), title, description, tags(json), source, license_note,
  file_key, url, sha256, bytes, width, height, duration_ms, created_at, updated_at
  index(user_id, kind), index(user_id, sha256) 唯一, index(user_id, created_at)

content_draft            稿件（主记录，含当前正文）
  id, user_id, title, topic, body_md, status(enum), tags(json), due_at,
  current_version, created_at, updated_at
  index(user_id, status), index(user_id, updated_at)

content_draft_version    稿件版本（每次保存一条）
  id, user_id, draft_id, version, body_md, summary, created_by, created_at
  unique(draft_id, version)

content_draft_asset      稿件↔素材
  id, user_id, draft_id, asset_id, role(enum: 配图/引用/参考), anchor, created_at
  unique(draft_id, asset_id, role)

content_publication      发布台账（含排期与结果）
  id, user_id, draft_id, channel, variant_title, variant_body_md,
  planned_at, published_at, url, status(enum: 待发/已发/失败/撤回), error, retries,
  metrics(json), created_at, updated_at
  index(user_id, channel, status), index(user_id, planned_at)
```

设计取舍：

- **一稿多版**用 `content_publication.variant_*` 承载，而不是再开一张 variant 表 —— P0/P1 够用，避免表爆炸；若 P2 需要「版本本身再留历史」，再拆。
- 正文只存 Markdown；导出格式在读取时生成。
- 素材去重用 `sha256`（同用户内唯一），命中则复用而不是重复登记。
- 所有时间用 UTC 存储，展示层转本地。

## 6. API 草案（REST，均需登录）

```
GET    /api/content/assets?kind=&tag=&unused=        素材列表
POST   /api/content/assets                            登记素材（支持 sha256 去重复用）
PATCH  /api/content/assets/:id                        改元信息
DELETE /api/content/assets/:id                        删除（被引用则拒绝，返回引用稿件）

GET    /api/content/drafts?status=&q=&tag=            稿件列表
POST   /api/content/drafts                            新建稿件
GET    /api/content/drafts/:id                        详情（含版本数、关联素材、发布记录）
PATCH  /api/content/drafts/:id                        保存正文（自动生成新版本）
GET    /api/content/drafts/:id/versions               版本列表
POST   /api/content/drafts/:id/rollback               回滚到指定版本
POST   /api/content/drafts/:id/assets                 关联素材 / 解除关联

POST   /api/content/publications                      建排期或登记发布
PATCH  /api/content/publications/:id                  改状态/回填链接与数据
GET    /api/content/publications?channel=&status=     台账
GET    /api/content/drafts/:id/export?channel=        生成可直接粘贴的成品包

GET    /api/content/stats?from=&to=                   P2：产出与复用
```

权限：全部按 `user_id` 隔离；写操作沿用现有「确认档」策略；删除仅 Owner。

## 7. 非功能需求（硬约束）

1. **不破坏现有契约**：不改既有表与字段语义；新增表只做 `AutoMigrate` 追加。
2. **可回退**：迁移只增不改；`content_*` 表可整表删除而不影响其他功能。
3. **多用户隔离**：任何查询不得漏 `user_id`（沿用 `internal/web` 现有写法，测试要覆盖跨用户不可见）。
4. **性能**：稿件列表/素材列表走索引；正文只在详情接口读取（列表不返回 `body_md`）。
5. **安全**：素材 URL 与文件键不允许路径穿越；导入 Markdown 不执行 HTML（前端渲染沿用现有 sanitize）。
6. **可观测**：新增 `GET /api/content/health`（表是否存在、条数），便于排障。
7. **失败不阻断**：Agent 工具检索失败要降级为「无结果」，不能中断对话（沿用记忆注入的做法）。

## 8. 验收标准（可测）

- A1 素材登记去重：同 `sha256` 二次登记返回同一 id，且不新增行；
- A2 稿件每次保存生成新版本，版本号连续、可回滚，回滚也留版本；
- A3 删除被引用素材被拒绝，错误里列出引用稿件 id；
- A4 跨用户读写全部 403/404，测试覆盖列表、详情、删除；
- A5 状态机非法跳转被拒绝（如 已发布→草稿 需显式「撤回」动作）；
- A6 发布台账按渠道+状态筛选正确，重试次数与失败原因可查；
- A7 Agent 只读工具在 DB 未初始化时返回降级结果而不是报错中断；
- A8 `go build ./...` 与全量测试全绿，新增表不影响老库启动。

## 12. 已落地（2026-10-21，仅数据库层）

按「**只要数据库就行了**」的口径，本次只交付数据层，HTTP API / Agent 工具 / 界面一律不做。

**新增文件**

- `internal/model/content.go`：5 张表 `content_asset` / `content_draft` / `content_draft_version` / `content_draft_asset` / `content_publication`，全部带 `user_id`；索引按「列表页最常用的筛选」建（user+kind、user+status、user+updated、user+channel+status、user+planned、draft+version 唯一、draft+asset+role 唯一）。
- `internal/model/db.go`：AutoMigrate 追加这 5 张表（只增不改，老库启动不受影响）。
- `internal/content/rules.go`：纯校验与状态机——稿件 `idea→draft→review→final→scheduled→published→archived`（允许打回与归档重开，禁止跳级）、发布台账 `planned→published/failed/withdrawn`（失败可重排）、标签编解码、标题归一、素材类型/用途白名单、统一错误 `ErrNotFound/ErrInvalidKind/ErrInvalidStatus/ErrBadTransition` 与 `AssetInUseError`。
- `internal/content/store.go`：数据访问层，方法全部以 `userID` 为第一参数并强制带进 where（多用户隔离）；素材按 `(user_id, sha256)` 去重复用；稿件保存走**行锁 + 追加版本**（避免并发算出同一个 version 撞唯一键）；回滚不是改历史而是追加新版本；删素材前查引用，被引用返回 `AssetInUseError` 不级联；发布台账状态机 + 失败留原因且 `retries+1`；`ExportDraft` 有平台定制版用定制版、否则回落主正文。
- `internal/content/rules_test.go`：8 组纯逻辑用例（状态机正反例、标签、标题、输入校验、用途、分页、未绑库报错），默认门禁即跑。
- `internal/content/store_db_test.go`：4 组真 MySQL 用例（去重与跨用户隔离、版本链与回滚、删除保护、发布生命周期与导出），默认 `t.Skip`，设 `CONTENT_IT=1` 才跑；用例只操作自造 userID 并在结束时清库。

## 13. 已落地（2026-10-24，排期自动导出任务）

按「实现一个自动任务」的口径，只做**到点导出**：扫到期排期 → 生成成品包落盘 → 台账推进到 `exported`，
失败按指数退避重试。仍然遵守 §10 第 1 条：**不做真实平台发帖**，也不写 `published_at`。

**新增/改动**

- `internal/model/content.go`：`content_publication` 增加 `next_attempt_at` —— 一列两用：失败后的退避时间，
  以及 worker 领取时的租约（进程崩溃后租约到期自动重捡，不需要额外的「处理中」状态）。
- `internal/content/rules.go`：发布台账新增 `exported` 状态和对应转移。自动任务只推进到「已导出」，
  人工贴完再 `exported → published` 回填 url —— 不让台账谎报一条不存在的线上链接。
- `internal/content/publish.go`：成品包渲染（标题/渠道/计划时间/标签/正文/素材清单）、文件名归一
  （`Slugify` 按 rune 截断）、`SafeSegment`（防 `../` 越出导出目录）、`BackoffFor`（1min 起翻倍，上限 1h）、
  默认 `PackagePublisher` 落盘实现；`Publisher` 接口留给以后的平台草稿箱/对象存储。
- `internal/content/store_jobs.go`：到期扫描（`planned` + `planned_at<=now` + 不在退避/租约 + 关联了稿件）、
  待导出计数、`ClaimPublication`（条件更新领取，天然防并发重复导出）、`MarkExported`、
  `RecordExportFailure`（累计次数，用尽落 `failed` 并留原因）。
- `internal/content/runner.go`：`Runner.RunOnce` 串行跑批（TryLock，上一轮没完直接返回 Busy）、
  支持只跑某个用户、内存历史 200 条、`Status`/`CountDue`/`Recent`。
- `internal/web/content_jobs.go`：`GET /api/content/jobs`（状态/待导出数/最近记录）、
  `POST /api/content/jobs/run`（立刻跑一轮，只处理当前用户）；后台调度由 `app/server.go` 启停。
- 配置：`CONTENT_PUBLISH_INTERVAL_MINUTES`（默认 5，`<=0` 关闭，手动触发仍可用）、
  `CONTENT_EXPORT_DIR`（默认用户配置目录下的 `blog-my\content-publish`，安装版也有写权限）、
  `CONTENT_PUBLISH_BATCH`（默认 20）、`CONTENT_PUBLISH_MAX_ATTEMPTS`（默认 3）。
- 测试：`job_test.go`（无库：退避/文件名/渲染/整轮分支/并发 Busy）、`store_jobs_db_test.go`
  （真库：领取与租约、退避、跨用户隔离、真库端到端，`CONTENT_IT=1` 才跑）、
  `internal/web/content_jobs_test.go`（env 解析、开关、接口形状、用户隔离）。

**验证**：`go build ./...` 通过；`go test ./...` 全绿；另用独立测试库 `blog_my_content_it` 跑了
`CONTENT_IT=1` 的 8 个真库用例（含新增 4 个，其中一条是真库端到端）全绿。

**明确没做**：稿件/素材/台账的 HTTP CRUD（F1~F5）、Agent 工具（F7/F8）、界面入口。排期目前仍需直接调
`content.Store`（或等后续接口）创建；自动任务只消费已有台账。
