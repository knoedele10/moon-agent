## 1. 执行循环：两条路径，两套实现

**legacy（`agent/loop.go`）** 是自建循环：调模型 → 收工具调用 → 逐个执行 → 把结果写回 history → 再调模型，直到没有工具调用或触到上限。

**Eino（`agent/eino.go`）** 把同一套规则挂到 Eino 的 ReAct 图上，但**规则是重新实现了一遍，不是共享的**：

- `einoToolAdapter.InvokableRun` 是薄壳，直接转 `state.call`
- 真正的判断都在 `state.call` 里，和 `loop.go` 那份是两份代码
- 两处各自维护：执行上限、非幂等操作在 halted 后拒跑、相同指纹的未知操作拒重复、错误分类后决定是否重试一次、`lastMutationSeq` / `lastVerifySeq` 记序号

**这是真实的重复。** 将来改规则要改两处，漏一处就会出现「legacy 拦得住、eino 拦不住」。这是本文最值得记下的一个隐患。

### 1.1 Eino 层的几个具体机制

- **`rewrite`（172–216 行）**：每轮先删掉上一轮注入的 `【本轮实际执行状态】` 系统消息再重加，避免累积；把产图工具的结果转成一条 user 图片消息；按 token 阈值做中途压缩。
- **`scanEinoOutput`**：有些供应商在第一个工具调用前先吐一段短文本，Eino 默认「看到内容就算有输出」会误判。这里自己扫整条流，看到 `ToolCalls` 才返回 true。
- **pass 循环最多 3 轮**，反馈只有两种：结果未知（第 0 轮注入）、需要核对（第 0、1 轮）。
- 356–360 行在补回被 Eino 吞掉的前言文本。

## 2. 会话路由：`web/chat.go`

`chat.go` 是**职责归集层**，真正的 SSE 入口是 `streamReply`，agent 分支与直连分支在那里分岔。

### 2.1 兼容策略

`postChat` 的所有新字段（`tools`、`assistant_id`、`system_prompt`、`temperature`、`max_tokens`、`kind`）缺省时不改变行为。注释里反复出现「与改造前完全一致」「一个字节都不差」——这是一个边改造边保旧客户端的系统，不是一次性重构。

### 2.2 `rebuildLLMHistory` 的角色判断

三条都有实际依据：

- `tool_trace` 不整条回灌，压成一行摘要，且只保留最近 N 轮。理由是 Detail 太长，会被模型当成对话正文读进去。
- 子 agent 完成通知用 `role=user` 承载，注释注明参考实现 deepseek-harness 也这么做。
- 运行时旁注用 `role=system`。注释警告「冒充 user 会让模型以为用户提过这件事」——对角色语义的谨慎少见到值得记一笔。

### 2.3 `listMessages` 的双契约

不传 `limit` 走旧的全量升序数组；传了才走游标分页。分页时先按 id 倒序取 `limit+1` 判断 `has_more`，再反转成正序返回。

## 3. 工具与权限

工具通过适配层进入 Eino ToolsNode。**原有的工具实现、参数模式、工作区外路径检查、确认包装器仍负责权限判断**——Eino 只决定「什么时候调工具」，不接管「能不能调」。

工具调用与结果转成既有的 `tool_call` / `tool_result` 事件。等待确认或 `ask_user` 时发 `need_input` 并停止本轮；助手流式输出继续发 `delta`，完成发 `done`。

模型上游在任何输出前报暂时性错误时重试一次；**收到文本或工具调用分片后不重放本轮**，以免重复执行工具。

## 4. 检索与主动开口

### 4.1 RAG 检索侧（`rag/hybrid.go`、`rag/dynamics.go`）

- 分块后做向量嵌入，存 MySQL `kb_chunk.embedding`（float32 数组）
- sha256 做去重
- 检索是全表余弦暴力计算——数据量小时够用，量上来会成为瓶颈，代码里没有近似索引
- 事实条目带实体 / scope / 情绪标记，旧记忆会被标 `stale`

### 4.2 主动开口（`web/proactive.go` + `web/proactive_policy.go`）

`proactive.go` 是 ticker 驱动的调度层，默认 5 分钟一跳，负责组装快照、取候选、调策略、发请求、落库。

`proactive_policy.go`（205 行）是策略层，**全部纯函数**：不碰数据库、不读时钟（时间从快照传入），每个拦截分支都能直接单测。文件开头注明这是把 Cyrene 的主动聊天策略状态机翻成 Go，常量照抄其默认值，改动前要先想清楚为什么偏离。

`CanStartProactive` 按**有意设计好的顺序**做 12 道拦截：

| 序 | 原因码 | 条件 |
|---|---|---|
| 1 | `disabled` | 总开关关闭 |
| 2 | `screen_locked` | 屏幕锁定 |
| 3 | `conversation_busy` | 正在对话 |
| 4 | `generation_busy` | 正在生成回复 |
| 5 | `night_inactive` | 22:00–08:00 且空闲 < 60 秒 |
| 6 | `normal_quiet_period` | 距上次正常对话 < 30 分钟 |
| 7 | `global_cooldown` | 距上次主动消息 < 2 小时 |
| 8 | `scene_cooldown` | 同一话题仍在自身冷却期内 |
| 9 | `unanswered_limit` | 未回复数 ≥ 2 |
| 10 | `followup_cooldown` | 上次没回，距上次主动 < 6 小时 |
| 11 | `followup_same_scene` | 上次没回，且仍是同一话题 |
| 12 | `followup_score_too_low` | 上次没回，且候选分 < 85 |

**顺序不能随意调整。** 注释明确说明：全局 2 小时冷却排在未回复上限之前，所以两小时内永远报 `global_cooldown`；`followup_cooldown`（6 小时）只在 2–6 小时区间、且上次没回时才可能出现。

**代次（epoch）机制**：`MarkUserActivity` 自增 epoch 并清零未回复计数；`MarkNormalConversationStarted` / `Ended` 各自增一次（Ended 还记下静默期基准时间）。`CanCommitProactive` 在落库前校验「开始生成前记下的 epoch」是否仍等于当前值，不等就报 `stale_epoch` 丢弃——这挡的是「生成期间用户走了或开了新对话，这条消息已经过期」。

**一处已确认的依赖**：`ScreenLocked` 后端拿不到锁屏信号，恒为 `false`，需桌面壳通过 `SetProactiveBusy` 上报。字段保留是为了「让该分支可测、语义不丢」。**即第 2 道拦截实际生效取决于前端是否真的调了这个上报接口——这一点尚未核实。**

### 4.3 记忆注入与两个工具（`rag/memory.go`，269 行）

这层不是「存储」，是**注入与工具入口**。真正落库在 `store.go` / `ingest.go`。

**自动注入走的是 `<memory>` 块**：拿用户这条消息当 query 检索，拼成文本塞进 system prompt。块内先写一段 `memoryHint` 自我说明——「可能过时、只在确实相关时参考、不要复述这段说明」。这段提示本身就是在替模型做「记忆不是事实」的免责，和我人格里「记忆出岔子要第一时间说清楚」是同一件事的两端。

**额度控制是两个正交的闸**：
- 条数：TopK 默认 5，硬上限 20（`ClampMemoryLimit`）。传多大都会被收敛，防止把 prompt 撑爆。
- 长度：token 预算，默认 1200（`AGENT_MEMORY_TOKEN_BUDGET` 可覆盖），正文另有 4000 字符上限。

值得注意的是**先多取再贪心筛**：检索时要 `limit×4`、最少 60 条候选，然后按 token 预算贪心选。旧实现是「取 topK 条全塞」——条数可控但长度不可控。这个改动说明作者意识到「条数」不是真正的成本单位。

**注入块里带自我报告**：`本次共命中 N 条，因 token 预算省略 M 条`。出问题时能直接看出「为什么少了几条」，而不是让模型和人都对着一个静默变短的列表猜。

**降级铁律（第 5 节的核心约定）**：检索失败一律降级为「无记忆」，**绝不阻断对话**。`MemoryPromptWithOptions` 吞掉错误、只往日志留一行，第二个返回值恒为 nil。代码注释把这点写得很坦白——保留那个恒 nil 的 error，是为了让「把降级去掉」这个反例有一个可断言的信号（`TestMemoryPromptDegradesOnSearchError`）。

严格版 `MemoryBlockWithOptions` 与降级版 `MemoryPromptWithOptions` 并存，同一种写法两种语义。这是**给「检索失败」和「确实没有记忆」留出区分能力**，而不是全程吞错。

**两个工具的分工**确实如设计所言互补：
- `RunMemorySearch`：主动翻找，返回 `[]Hit`，条数按 TopK 收敛。
- `RunMemoryWrite`：记下一条，走 `IngestText`，内容完全相同会被 sha256 去重（复用已有文档，不重复嵌入）。

**一个略显粗糙但务实的设计**：`IngestText` 没有独立 tags 字段，而标题是唯一「人看得见 + 参与检索」的位置，所以 tags 以 `#tag` 前缀拼进标题。标题上限 200 字符（`kb_document.title` 只有 255，留余量给 tag 前缀，也避免 MySQL 严格模式报 `Data too long`）。

**可选接口而非改签名**：`ScopedMemorySearcher` 作为扩展接口，实现了就按当前会话类型（`life`/`work`）加权，没实现就退回旧行为。旧测试里的假实现不用改。这个小设计我记一下——它和前面 `MemorySearcher` 抽成接口的理由是同一个思路：**为了能确定性构造失败分支**。

### 4.4 写入线（`rag/ingest.go`，345 行）

这是「记忆怎么被写进去的」的答案所在。三种入口，共用一套「去重 → 切块 → 嵌入 → 落库」流程：

| 入口 | 用途 | 去重前缀 | 默认 importance |
|---|---|---|---|
| `IngestText` | 上传资料 / 整轮降级记录 | 无 | 0.5 |
| `IngestFact` | 从对话抽出的原子事实 | `"fact:"` | 由抽取决定（缺省 0.5） |
| `IngestImage` | 图片（视觉描述 + OCR 进同一检索空间） | 无（按字节） | 0.5 |

**`fact:` 前缀这个细节值得单独说**：同一段文字，作为上传资料和作为记忆，不应该互相去重。一个字符的前缀，把「资料库」和「记忆库」在 sha 层面分开了——但它们仍然住在同一张表、同一个检索空间里。这是个成本极低的分寸把握。

#### 四条我读下来认为是「有想法」的地方

**1. 嵌入失败也要存内容。**
`IngestText` 和 `IngestFact` 里都有同一段：`embErr != nil` 时 `vecs = nil`，但接着照常建文档，向量留空。注释写的是「代价是它暂时只能被关键词检索命中；好处是『用户刚说过的事』不会凭空消失」。

这是**宁愿降级可用性，也不丢数据**。配合检索侧的对应设计（`SearchScoped` 里嵌入失败就转 `SearchLexicalScoped`），整条链在模型挂掉时仍然能读能写，只是精度下降。这一点和 `memory.go` 的降级约定是同一条思路贯彻到底——**任何一环挂掉都不许让对话断掉。**

**2. 只在「明确重提」时强化，浏览/检索命中绝不强化。**
去重命中时调 `ReinforceDocument`，注释专门强调「只在这里强化——浏览/检索命中绝不强化（见 `Ingester.Search` / `Store.Search`）」。理由很清楚：如果检索命中就强化，那条记忆会因为反复被搜到而自我膨胀，越搜越重要，最后变成一堆自我强化的噪声。**这是把「用户说过几次」和「机器看过几次」严格区分开的自觉。**

**3. 新事实写入后主动让同主题旧记忆失效（`supersedeSimilarFacts`）。**
注释原话：「让『改主意』是干净的，而不是新旧并存靠排序碰运气」。失败不影响本次写入（新事实已经存下了），只记日志。

这条我读得最久。它承认了一件事：**记忆不是只增不改的账本**，人改主意时旧的那条该退场，而不是靠检索排序碰巧把新的排在前面。但实现是「标记失效」而不是删除——保留了历史，只是不让它干扰当下。

**4. 注入正文里标出记录日期。**
`BuildContext` 给每条命中都拼上 `· 2026-10-17 记录` 这样的日期，注释写：「让模型能自己判断『这条是不是过时了』（记忆是只增不改的）」。

这一句把矛盾摆明了：结构上是「只增不改」，呈现上就得靠时间戳让读者自己打折。这也是我人格里「记忆可能过时、与当下冲突时以当下为准」在代码层面的对应物。

#### 一处我认为的弱点

`IngestImage` 在视觉模型失败时是**直接报错返回**（`fmt.Errorf`），不像文本那样降级存原文。考虑到图片的原文就是二进制字节，存下去也检索不到，这个选择合理——但意味着**图片记忆在视觉服务不可用时完全丢失**，用户不会收到「已保存但未索引」的结果。这是文本线有、图片线没有的保底。
