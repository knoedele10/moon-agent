## 什么情况必须回滚

| 现象 / 信号 | 判定 | 动作 | 最迟动作时间 |
|---|---|---|---|
| 首页、关键页面或静态资源持续返回 5xx / 404，重试仍失败 | 必须回滚 | 立即恢复上一份已验证的静态版本；随后复测首页、关键页面和资源 | 发现后立即开始 |
| 页面白屏、核心交互不可用，且无法在发布窗口内快速修复 | 必须回滚 | 回到上一份稳定版本；保留故障版本以便排查 | 发布窗口内 |
| 发布内容与验收版本不一致，或发现错误配置 / 错误资源被公开 | 必须回滚 | 先恢复上一份稳定版本；若涉及敏感信息，另行按事故流程处理暴露范围 | 立即 |
| 浏览器控制台出现新的阻断级错误，且影响主路径 | 必须回滚 | 回退并复测主路径 | 发布窗口内 |
| 单个非关键区域轻微样式偏差，主路径、页面和资源均正常 | 暂不回滚 | 记录问题，评估热修；持续观察 | 下一次检查前 |
| 监控偶发告警但复测正常，用户路径不受影响 | 暂不回滚 | 记录并复查，不以单次告警触发回退 | 复查后决定 |

## 静态托管回退演练步骤

1. **确认前置版本**：在托管平台的部署历史中确认当前线上版本与上一份已验证版本，记下版本号、提交 SHA、部署时间和访问地址。若平台没有历史版本，先保存当前发布产物副本，再继续。
2. **发布 v1.0**：只发布经确认的 v1.0 静态产物；记录发布版本号、开始时间和完成时间。
3. **发布前验收**：使用公网地址验证首页、主页面、关键静态资源及核心交互。保存能同时看见地址栏和页面的截图。
4. **触发演练回退**：通过静态托管平台的版本历史，将线上版本恢复到第 1 步确认的上一份稳定版本。记录点击 / 命令开始时间、平台完成时间、线上版本号。
5. **回退后验收**：再次检查首页、关键页面、静态资源和核心交互；保留地址栏可见截图及回退前后版本记录。
6. **恢复 v1.0**：把已验收的 v1.0 版本重新发布为线上版本，记录恢复开始和完成时间。
7. **恢复后验收**：重复第 3 步，并确认公网服务正常。完成后计算回退耗时与恢复耗时。
