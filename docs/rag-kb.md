# 本地多模态 RAG 知识库设计（kb）

> 状态：**设计文档**。本文说明打算怎么做、以及已经建好的表结构。
> 除 MySQL 版本（5.7.19，项目环境给定）外，本文不含任何「已实测通过」的性能或效果结论；
> 没跑过的部分一律写成「设计如此」或「待验证」，不把设想写成结果。

## 1. 目标与非目标

### 目标
- **本地**：嵌入模型 `bge-m3` 与视觉模型 `qwen2.5vl:7b` 都跑在本机 Ollama 上，断网也能用。
- **多模态**：文本和图片走同一条检索链 —— 图片先由视觉模型转成「描述 + OCR 文本」，再和文本块一起被嵌入、被检索。
- **零额外依赖**：向量就存在已有的 MySQL 里，不额外起向量库进程，备份/迁移只需照看好数据库。
- **可审计**：原始字节和向量都能直接用 SQL 看到，排查问题不必进二进制索引。

### 非目标（明确不做）
- **不做分布式**：单机、单 MySQL 实例，不涉及分片、多副本、跨节点检索。
- **不做大规模向量库**：不引入 Milvus / Qdrant / pgvector 等，也不做 ANN（HNSW / IVF）。
- **不做重排（rerank）**：只有「嵌入 + 余弦 topK」，没有 cross-encoder 二次排序。
- **不做权限隔离**：当前 `user_id` 只是归属标记，接口层不按用户过滤（见第 6 节）。

## 2. 整体架构

写入链路：

```
上传文件（文本 / 图片）            直接入库一段文本
        │                          │
        │  POST /api/kb/documents  │  POST /api/kb/text
        ▼                          ▼
   按扩展名 / MIME 判定 kind ───────────────┐
        │                                   │
   text ┤                                   │
        └─ image ─▶ qwen2.5vl:7b 看图        │
                   生成「描述 + OCR 文字」    │
                        │                   │
                        ▼                   │
                  得到一个 image_caption 文本 │
                        │                   │
        ┌───────────────┘                   │
        ▼                                   │
   文本切块（chunk）◀───────────────────────┘
        │
        ▼
   bge-m3 嵌入 → 1024 维 float32（4096 字节 / 块，按块各一条）
        │
        ▼
   MySQL 落库：kb_document（原始字节） + kb_chunk（文本 + 向量）
```

查询链路：

```
用户提问 query
        │
        ▼
   bge-m3 把 query 嵌入 → 1024 维向量
        │
        ▼
   暴力余弦：遍历全部 kb_chunk 向量，算相似度，取 topK
        │
        ├─ 命中文本块 ─▶ 取块文本
        └─ 命中图片块 ─▶ 取块文本「描述+OCR」 + 按 image_path 回捞 kb_document.content 原图
        │
        ▼
   拼上下文（块文本 + 出处：文档标题 / 块序号 / 是否图片）
        │
        ▼
   LLM（本地 qwen2.5:7b / qwen3:4b 或云端模型）
        │
        ▼
   带出处的回答（SSE 流式返回）
```

图片块命中时，设计上会把 `kb_document.content` 里的原图作为**多模态消息**和文本一起喂回生成模型，让回答能「看着原图说话」。
注意这依赖生成模型本身支持多模态 —— 现有的 `qwen2.5:7b` / `qwen3:4b` 是纯文本模型，真要回图需要另选多模态生成模型，这一点**待验证**。

## 3. 为什么这么选

### 为什么嵌入模型选 bge-m3
- **多语言**：知识库里中英文混排很常见，bge-m3 的多语言能力比多数单语模型稳。
- **1024 维**：维度和体积折中。每块向量 1024 × 4 = 4096 字节，几万块也只有百来 MB 量级，MySQL 存得下、内存放得进。
- **本地可跑**：Ollama 一条 `ollama pull bge-m3` 就有，离线可用、没有调用费用，也避免了把私人文档发到云端。

### 为什么向量存 MySQL，用 LONGBLOB 而不是上向量库
- **量级够用**：个人知识库是几千到几万块，暴力检索能扛住（见下方复杂度分析），没必要为它引入新进程。
- **零额外依赖**：项目本来就有 MySQL，多一个向量库就多一套安装、升级、备份、一致性要操心。
- **可直接 SQL 审计**：`select id, kind, length(embedding) from kb_chunk` 就能看见向量的维度和存在性；出问题时能一条 SQL 定位，不用进二进制索引翻。
- **代价**：放弃 ANN 索引，检索是全表线性扫描。这是有意识接受的代价，容量上限写在下面。
- **细节**：向量按 1024 个 float32、小端字节序直接写进 `LONGBLOB`；`dim` 冗余一列，读出来先校验字节数与维度是否自洽。

### 暴力检索的复杂度与容量上限
- **单次查询复杂度**：O(N · d)。N = 块数，d = 1024。一次检索要对 N 个向量各做一次 1024 维点积。余弦相似度靠「写入时先归一化、查询时点积即余弦」来省掉开方。
- **粗估（设计推算，非实测）**：单核 Go 大约每秒能做 1e8～1e9 次乘加量级。
  - N ≈ 1 万 → 约 1.0e7 次乘加 → 毫秒级；
  - N ≈ 10 万 → 约 1.0e8 次 → 几十毫秒级，仍可接受；
  - N ≈ 100 万 → 约 1e9 次 → 秒级，必须并行 + ANN 才舒服。
- **真正的卡点不在 CPU，而在内存与 I/O**：每块 4 KB 向量，10 万块就是约 400 MB。如果每次查询都从 MySQL 把全部向量读出来，网络/磁盘 I/O 会先顶不住。所以实用做法是启动时把 `(id, document_id, seq, kind, dim, embedding)` 预加载进内存（或做一层带失效的内存缓存），查询只在内存里算，**待验证**。
- **结论（设计口径）**：几千～几万块是舒适区；到十万级需要「向量常驻内存 + 多 goroutine 并行 + 先按 user_id / kind 预过滤」；到百万级就该换 ANN 方案，届时再评估上向量库。

## 4. 表结构说明

### `kb_document`（一行 = 一个文档）
| 字段 | 类型 | 作用 / 为什么 |
|---|---|---|
| `id` | BIGINT UNSIGNED | 自增主键。文档是流水型数据，数字 id 比 UUID 省空间、插入快。 |
| `user_id` | VARCHAR(36) | 归属用户，关联 `user.id`；**空串表示公共知识库**。可空，与 GORM 模型一致。 |
| `kind` | VARCHAR(16) | `text` / `image`，入库时按扩展名 + MIME 判定。 |
| `title` | VARCHAR(255) | 标题，取文件名或调用方指定；保证列表页有可显示的名字。 |
| `source` | VARCHAR(512) | 本地路径或 URL，可空（浏览器上传常常没有来源）。 |
| `mime` | VARCHAR(64) | MIME 类型，可空（可由扩展名兜底）。 |
| `bytes` | BIGINT | 原始字节数，冗余存一份，列表展示不必回读 LONGBLOB。 |
| `sha256` | CHAR(64) | 内容指纹，**唯一键**用于去重；可空（流式写入可能暂无指纹，NULL 不参与唯一冲突）。 |
| `content` | LONGBLOB | 原始内容：文本存 UTF-8 字节，图片存原图字节。不落磁盘，只进数据库。 |
| `meta` | TEXT | 附加 JSON（图片宽高、视觉模型名等），可空。 |
| `chunk_count` | BIGINT | 切块数量，冗余存储便于列表展示；`NOT NULL DEFAULT 0`，先建文档后补块时不会为空。 |
| `created_at` | DATETIME(3) | 创建时间，毫秒精度。 |

### `kb_chunk`（一行 = 一个可检索块）
| 字段 | 类型 | 作用 / 为什么 |
|---|---|---|
| `id` | BIGINT UNSIGNED | 自增主键。块远多于文档。 |
| `document_id` | BIGINT UNSIGNED | 所属 `kb_document.id`，非空，建索引；只做逻辑关联、不建物理外键。 |
| `seq` | BIGINT | 文档内序号，从 0 开始，用于稳定排序。 |
| `kind` | VARCHAR(16) | `text` / `image_caption`，区分文本块与图片转写块。 |
| `text` | MEDIUMTEXT | 检索与展示的正文：文本块正文，或图片块的「描述 + OCR」。 |
| `image_path` | VARCHAR(512) | 仅图片块用：指向所属文档，便于溯源到原图；文本块为空。 |
| `embedding` | LONGBLOB | 1024 维 float32 小端数组 = 4096 字节。 |
| `dim` | BIGINT | 维度冗余存储，读向量时做自洽校验。 |
| `created_at` | DATETIME(3) | 创建时间，毫秒精度。 |

> **与 GORM 模型的对齐说明**：本文件的 DDL 逐字段对齐 `model/kb.go` —— `user_id` / `bytes` / `source` / `mime` / `sha256` / `meta` / `image_path` 可空，`kind` / `title` / `content` / `chunk_count` / `document_id` / `seq` / `text` / `embedding` / `dim` 非空，`chunk_count` 带 `DEFAULT 0`。唯一需留意：`sha256` 本文件写成 `CHAR(64)`（定长 hex，utf8mb4 下唯一索引占 256 字节，在 5.7 的 767 字节上限内）；若模型侧写成 `size:64`，GORM 会生成 `varchar(64)`，两处需取其一对齐。

### 为什么图片要存「描述 + OCR 文本」，而不是只存图片
`bge-m3` 是**文本**嵌入模型，不能直接对图片出向量。如果只把图片塞进库，图片就进不了和文本同一条检索链，检索时永远命中不到它。
所以流程是：**图片 → qwen2.5vl:7b 生成「描述 + OCR 文字」→ 这段文字再走 bge-m3 嵌入，和文本块一起参与检索**。
这正是本方案能叫「多模态」的关键：模态差异在**入库时**就被抹平成文本，检索链自始至终只处理文本向量。
原图本身仍完整存在 `kb_document.content`（LONGBLOB），有两个用途：一是溯源/展示，二是命中图片块后把原图作为多模态消息回喂给支持视觉的生成模型。

## 5. 接口清单

> 以下为**已冻结**的契约，前后端与实现按此对齐，不自行改动。

- `POST /api/kb/documents`（multipart/form-data，字段名 `file`）：上传一个文本或图片文件，服务端按扩展名/MIME 判定 kind
- `POST /api/kb/text`（JSON `{"title":"...","text":"..."}`）：直接入库一段文本
- `GET /api/kb/documents`：列出知识库文档
- `GET /api/kb/documents/:id`：单个文档详情（含各块文本）
- `DELETE /api/kb/documents/:id`：删除文档及其所有块
- `POST /api/kb/search`（JSON `{"query":"...","top_k":5}`）：只检索，返回命中块与相似度
- `POST /api/kb/ask`（JSON `{"query":"...","model":"...","top_k":5}`）：检索 + 交给模型生成带出处的回答（SSE 流式）

## 6. 已知限制与后续

- **没有重排**：只有余弦 topK。语义相近但无关的块会混进上下文；后续可加轻量 rerank（本方案暂不做）。
- **没有增量索引**：改动/重新上传文档会重算切块与向量；暂不做只增量更新变化块。删除走 `DELETE /api/kb/documents/:id` 连同块一起删（逻辑设计如此，**待验证**实现）。
- **没有权限隔离**：`user_id` 目前只是标记，检索与列表不按用户过滤；公共库与私有库在数据层没做硬隔离。多用户场景下这是已知缺口。
- **大图 / 多图文档**：原图字节整块进 LONGBLOB，超大图会让单行膨胀、影响读写；一份文档里多张图片目前按「一图一块」处理，图片很多时块数会明显上升。具体表现与切图策略**待验证**。
- **根本依赖：视觉描述质量决定图片能不能被检索到**。图片本身不产生向量，全靠 qwen2.5vl:7b 生成的「描述 + OCR」文本。描述漏了某个细节，或 OCR 对模糊/艺术字识别不准，对应图片就永远检索不到 —— 这是本方案最脆弱的一环，也是效果上限所在。**待验证**：不同类型图片（截图 / 照片 / 手写 / 表格）的召回表现。
- **多模态回喂受限**：把原图作为多模态消息喂回生成模型，取决于生成模型是否支持视觉输入；现有本地文本模型不支持，此能力**待验证**。
- **性能数字为设计推算**：第 3 节的复杂度与容量上限是量级估算，未经真实数据实测；后续补充基准测试后再回填。
