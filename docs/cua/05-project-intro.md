## 2. 项目简介（约 420 字，可直接进申报书）

本项目在已有的桌面聊天客户端 `blog-my`（Electron 外壳 + Go/Gin 后端 + MySQL）之上，构建一套**完全本地运行**的桌面智能助手：它既能把个人文档与图片建成可检索、可溯源的知识库，也能通过视觉语言模型"看着屏幕"直接操作图形界面，完成那些没有 API 可调的重复性工作。

系统由两条互补的技术链构成。其一为**本地多模态 RAG 知识库**：文本按语义切块，图片先由视觉模型转写成"描述 + OCR 文字"，两者统一用 `bge-m3` 嵌入成 1024 维向量存入 MySQL，检索走余弦 topK，回答带出处并流式返回；模型、向量、原始文件全部留在本机，断网可用。其二为**视觉 CUA（Computer-Use Agent）**：截取屏幕画面交给视觉语言模型推理，模型只输出结构化的下一步动作（点击 / 输入 / 组合键 / 拖拽 / 滚动 / 等待 / 重截 / 结束），执行器把图像坐标换算成屏幕坐标后用 PyAutoGUI 执行，再把执行回执与新的截图送回模型，形成"观测—决策—执行—再观测"的闭环。

项目坚持"**能调 API 就不用鼠标**"：API、浏览器 DOM、白名单系统命令三级优先，GUI 视觉操控仅作兜底，用于第三方闭源桌面软件与老旧内部系统这类真正的盲区。动作协议、错误码、安全不变量均已冻结成可执行契约，为并行开发与后续回归评测提供稳定基线。

## 3. 背景与痛点

### 3.1 API 覆盖不到的盲区

真实工作里大量重复操作落在"没有接口"的地方：

- **第三方闭源桌面软件**：财务、医疗、工控、老旧行业软件，只提供图形界面，无 REST/SDK，官方也不打算提供。
- **跨应用的手工流程**：在浏览器查资料 → 复制 → 切到本地软件录入 → 回浏览器核对，每一步都有 API，但"串起来"这一步没有 API。
- **低频一次性操作**：为只跑一次的流程写 API 集成，开发成本远高于点几下，但纯手工又容易错。
- **天然在 API 之外的环节**：登录态、验证码、UAC 提权、支付确认——这些不是技术没做到，而是设计上就该由人来做。

这些盲区的共同点是：**机器没有结构化入口，只有像素**。

### 3.2 传统 RPA 的脆弱性

传统 RPA（录制—回放 / 控件树驱动）在真实环境里很脆：

- **绑定控件树或 DOM**：界面改版、控件重命名、换语言、换分辨率、换主题，选择器立即失效。第三方软件自绘界面（Qt 自绘、Electron 自绘、游戏引擎、远程桌面画面）根本不给稳定的控件树。
- **录制即假设**：录制时假定"第 3 个输入框就是金额"，运行时界面顺序一变就静默写错数据——比报错更危险。
- **没有"看清楚再动手"的能力**：回放脚本不会"读一眼前面发生了什么"，遇到弹窗、加载慢、二次确认只能靠固定 sleep 硬扛。
- **出错无判别**：多数脚本的操作返回值是"动作发出去了"，而不是"界面确实变了"。
- **无停手边界**：脚本一旦错位，会继续对着错误的界面点击，可能点到删除、覆盖、支付。

### 3.3 本项目的切入点

大语言模型的**视觉理解 + 结构化输出**能力，第一次让"看着屏幕做决定"变得可工程化：

- 不依赖控件树——模型直接看图，界面怎么画都能理解；
- 不依赖固定顺序——每一步都重新观测，弹窗和加载态能被"看见"；
- 输出可约束——动作被压成有限的 9 种结构化指令，不是自由文本、更不是模型现场生成的代码；
- 执行有回执——每一步都比对前后帧，判断"到底生效没有"。

代价必须说清楚：视觉路线**更慢、更贵、更不确定**，所以本项目把它定位成"最后手段"，而不是"默认手段"（见 4.4 四级路由）。

## 4. 技术原理

### 4.1 视觉语言模型如何把像素变成动作

链路只有四步，但每一步都必须有明确的输入输出契约：

    ① 截屏  →  ② 组装 Observation  →  ③ 视觉模型推理  →  ④ 解析为 Step 并校验

**① 截屏**：抓取全屏（或指定区域）的位图，同时记录这块图在真实屏幕坐标系里的原点与缩放比。

**② 组装 Observation**：把"模型这一步能看到的一切"打包成一个 JSON——当前截图、屏幕几何、上一步的执行回执、最近若干步的压缩历史、剩余步数与时间预算。这一步的设计要点是**压缩**：把完整截图历史全部喂回去会瞬间烧光上下文，所以历史只给摘要。

**③ 视觉模型推理**：模型同时拿到图片、任务描述、上一步结果和剩余预算，输出一个 Step：先写一句 `thought`（我看到了什么 → 所以我要做什么），再给出一个 `action`，可选给出 `expect`（预期结果 + 等待上限）。

**④ 解析与校验**：模型的输出**不保证是纯 JSON**——可能包在 Markdown 代码块里，可能前后带一句话。解析器按"直接反序列化 → 剥离代码围栏 → 扫描第一个平衡花括号对象"三级降级提取，再按 JSON Schema 校验。坐标落在图像外或参数越界，一律拒绝并回喂合法区间。

**为什么 `thought` 是必填而不是可选**：出错时它是最省时间的排障信息——一眼就能分清是"模型看错了"还是"模型想错了"，这两类问题的修法完全不同。

### 4.2 Observation → Step → ActionResult 闭环

三层数据、三个方向，构成一个可审计的循环：

| 层 | 名字 | 方向 | 生产方 | 消费方 |
|---|---|---|---|---|
| L1 | **Observation**（观测） | 执行器 → 模型 | 截图模块 | 视觉推理 Agent |
| L2 | **Step**（决策步） | 模型 → 解析器 | 视觉推理 Agent | 动作解析模块 |
| L3 | **ActionResult**（执行回执） | 执行器 → 编排器 | 键鼠执行模块 | 编排器 / 下一轮 Observation |

    L1 ──▶ L2 ──▶ L3 ──▶ L1 ──▶ … 直到 done=true 或触发终止条件

闭环的关键在 **L3 不是"动作发出去了"，而是"界面到底变没变"**：执行器在执行前后各取一帧缩略图，用感知哈希差分算出 `change_ratio`（变化像素占比），作为"这一步有没有生效"的客观依据，并把它连同耗时、错误码、最终光标位置一起回执给下一轮 Observation。

由此可以区分三类失败，这也是这类系统能不能用的分水岭：

- **动作失败**：报错、越界、键名不在白名单 → 按错误码表重试；
- **动作成功但界面没变**：`expect` 超时 → 再截一帧确认，仍不符预期则判定停滞；
- **动作反复成功但画面几乎不变**：连续 N 步无变化 → `E_STALL`，判定"这条路走不通"，**强制重规划**而不是继续重试；同一（动作，画面哈希）重复 3 次以上 → `E_LOOP`，回退到上一个稳定状态。

契约明确区分了"重试"与"重规划"：把"卡住"当成"超时"反复重试，是这类 agent 烧完预算却什么都没做成的最常见原因。

### 4.3 坐标空间与缩放（最容易出错的地方）

模型看到的坐标与鼠标要点的坐标**不是同一个空间**，中间必须做一次确定的换算：

- 模型输出的所有坐标，都在**当前这一帧 `image` 的像素空间**里，左上角为 `(0,0)`，不是屏幕空间，也不是上一帧的；
- 执行器负责换算：

      screen_x = origin.x + round(x / scale)
      screen_y = origin.y + round(y / scale)

  其中 `scale = image.width / 捕获区域宽度`；全屏捕获时 `origin=(0,0)`；局部捕获（`screenshot.region`）时 `origin` 为该区域左上角在虚拟屏幕坐标中的位置；
- Windows 的显示缩放（125% → `dpi_scale=1.25`）**只记日志、不参与换算**——因为截图 API 与 pyautogui 工作在同一个坐标系下，重复乘缩放反而会点偏；
- **超出图像边界的坐标一律拒绝（`E_OUT_OF_BOUNDS`），绝不 clamp**。clamp 会把"模型看错了"变成一个"点在了错误但合法的位置"的静默故障，后者更难排查。

这套设计还支持一个很实用的能力：当小字、密表格看不清时，模型可以请求**只截左上角那块区域并放大**，下一轮 Observation 的 `origin`/`scale` 随之改变，模型的后续坐标自动落在新的局部空间里——不需要模型自己记偏移量。

### 4.4 为什么用"截图—推理—执行"，而不是控件树或 DOM

这不是"视觉比 DOM 好"的问题，而是**覆盖面与稳定性之间的取舍**，本项目用四级路由把两者放在正确的位置：

| 级别 | 手段 | 典型例子 | 成本 / 稳定性 |
|---|---|---|---|
| **L0** | 结构化接口：REST / GraphQL / SDK / CLI / 本地 socket | 调 GitHub API 建 issue、`git` 命令 | 最快最稳，首选 |
| **L1** | 浏览器 DOM 层：CDP / Playwright | 网页表单填写、抓取 | 稳，不受分辨率影响 |
| **L2** | 操作系统命令（**白名单**约束） | 打开文件、复制目录 | 快，但权限语义要管住 |
| **L3** | **GUI 视觉操控**（本协议） | 第三方闭源桌面软件、只有图形界面的老旧内部系统 | 最慢最脆，**兜底** |

判定规则：从上往下命中第一个可用的就停；能力要**实测探测**而不是"文档说有 API 就算数"（探到 401 说明接口存在，DNS 失败说明不存在）；用了 API 也要校验结果（L0 同样会静默失败）。

**为什么仍然必须有 L3**：

1. **控件树不是普适的**。UIA / Accessibility / DOM 只在"愿意暴露结构"的软件上成立。自绘界面（Qt 自绘、Electron 自绘、游戏引擎、远程桌面画面、视频流里的界面）根本不提供稳定的控件树，查到的"控件"可能是空的、错位的、或随版本改名的。
2. **DOM 只覆盖浏览器内**。桌面软件、系统设置、传统客户端全在 DOM 之外；而这类软件恰恰是重复劳动最密集的地方。
3. **像素是唯一平台无关的接口**。换操作系统、换 UI 框架、换分辨率都不需要改协议——协议里没有"点击叫『确定』的按钮"这种语义动作，只有坐标，控件定位是视觉模型的职责 🔶。
4. **视觉能处理"以图为准"的信息**：图表趋势、图形状态提示、状态颜色、布局异常——这些在 DOM 里没有对应节点，但人靠看就能判断。

**为什么 L3 只做兜底**：视觉推理最慢、最贵、最不确定，且每一步都可能被弹窗/动画干扰。把 L3 用在"有 API 的地方"是纯粹的浪费，还会引入不必要的误操作风险。契约因此把 GUI 定位为"补上 API 覆盖不到的盲区"，而不是"用鼠标重写一遍 API 调用"。

### 4.5 本地多模态 RAG 的原理（图片怎么进入检索链）

嵌入模型 `bge-m3` 是**文本**模型，不能直接对图片出向量。如果只把图片塞进库，它就永远进不了检索链。所以本项目在**入库时抹平模态差异**：

    文本 ─────────────────────────────────▶ 切块 ─┐
                                                   ├─▶ bge-m3 嵌入(1024 维) ─▶ MySQL kb_chunk
    图片 ─▶ qwen2.5vl:7b 转写「描述 + OCR」 ─▶ 切块 ─┘

- 检索链自始至终只处理文本向量，图片的"可检索性"完全由转写质量决定；
- 原图字节完整保存在 `kb_document.content`（LONGBLOB），用于溯源展示，以及命中后的多模态回喂；
- 向量以 1024 个 float32 小端字节序存进 `LONGBLOB`（每块 4096 字节），并冗余一列 `dim` 做自洽校验；
- 检索是**暴力余弦**：把候选块向量取出、点积、排序取 topK。不做 ANN 索引，换来的是零额外向量库进程、纯 SQL 可审计、备份迁移只碰数据库一处 🔶；容量推演见 📐 [../rag-kb.md](../rag-kb.md) 第 3 节。

## 6. 关键创新点

### 创新点 1：API-first 的四级能力路由，把视觉操控限制在真正的盲区

**相比什么**：相比"纯视觉 RPA"（所有操作都靠截图找控件）和"纯 API 集成"（覆盖不到闭源软件）。
**好在哪**：契约把能力从 L0（API）到 L3（GUI 视觉）排成四级，命中第一个可用的就停。绝大多数操作走最稳的 L0/L1；只有真的没有任何可编程入口时才动用视觉。每次路由都记录 `{level, reason, probe_result}`，可以事后审计"为什么用了慢路径"。这让系统既不像纯视觉方案那样又慢又脆，也不像纯 API 方案那样一遇到闭源软件就无能为力。

### 创新点 2：冻结的三层动作契约 + 可执行 Schema，让"模型输出"变成可回归的接口

**相比什么**：相比让模型直接输出自由文本或现场生成 PyAutoGUI 代码的常见做法。
**好在哪**：模型只被允许输出 **9 种穷举动作**，包在固定的三层数据结构里，并配有 JSON Schema（draft 2020-12）做机器校验；解析器"宽进严出"——对模型的不规范输出三级降级提取（诚实处理它可能带 Markdown 围栏），但对未知动作类型、越界参数、非白名单键名一律硬拒绝。错误码表、重试次数、重规划条件是**冻结的**，不靠提示词里写"请不要乱来"。收益是可测试、可回归、可并行开发：契约不变，实现、测试、文档三条线可以同时推进。

### 创新点 3：把"停手"设计成第一优先级的安全不变量

**相比什么**：相比传统 RPA"录制即信任、错位继续点"的行为模式。
**好在哪**：执行器有一组无条件成立的不变量：`pyautogui.FAILSAFE` 永久开启且不对模型暴露开关；坐标越界拒绝而不 clamp；每步之间强制间隔，避免打爆 UI 事件队列；步数与墙钟**双重**预算；危险组合键默认关闭；`risk=high` 的动作默认需护栏放行；**任何异常终止都必须先释放所有按下的键**（否则会留下一个"Ctrl 卡住"的系统，之后用户所有点击都变成多选）；弹窗里的按钮文字命中**破坏性词表**（删除 / 卸载 / 格式化 / 支付 / 授权 / Delete / Uninstall / Pay / Grant…）时**不点击，直接转人工**。在这里"误点一个按钮"的期望损失远大于"少点一个按钮"。

### 创新点 4：图片"入库即转写"的零依赖多模态 RAG

**相比什么**：相比"图片走图像检索、文本走文本检索"的双塔方案，以及"引入 Milvus/Qdrant 等向量库"的重方案。
**好在哪**：图片在入库时就被视觉模型转成"描述 + 逐字 OCR"，之后和文本块走**完全相同**的嵌入与检索链路——一套索引、一次查询、一个排序，不需要跨模态对齐，也不需要额外服务进程。向量直接存 MySQL 的 LONGBLOB，可以用一条 SQL 检查向量的存在性与维度；备份、迁移、删除都只涉及数据库一处；全部模型本地运行，断网可用、无调用费用、私人文档不出本机。

### 创新点 5：知识与操作合流——"查得到"与"做得到"互相供给

**相比什么**：相比只有问答能力（能查不能做）或只有操作能力（能做但不懂业务）的单侧助手。
**好在哪**：RAG 检索出的领域知识与出处可以进入 CUA 的任务上下文，让"怎么做"有依据；CUA 每一步的截图、动作与执行回执又是一个天然的"过程档案"，可以回流成知识素材，供后续同类任务检索复用。两者共享同一套本地模型服务与用户体系，不需要用户维护两套工具。🔶 设计如此；具体接线方式与效果 ⏳ 待验证。

## 8. 应用场景

1. **闭源桌面软件的批量重复操作**：财务/医疗/工控/老旧内部系统中没有 API 的录入、核对、导出流程。系统先尝试 API 与命令行，都没有时才用视觉操控。
2. **跨应用的手工流程串接**：浏览器查资料 → 本地软件录入 → 回浏览器核对的固定链路。每一段走各自最稳的通道，串接环节由视觉闭环兜住。
3. **个人与团队的本地多模态知识库问答**：把文档与图片（截图、扫描件、图表）混在一起入库，用自然语言检索并得到带出处的回答；全程离线，适合内部资料。
4. **软件界面回归与可用性巡检**：对新版本界面截图做视觉核对（布局是否错位、关键按钮是否还在、提示文案是否变化），用视觉模型判断而不是靠脆弱的控件选择器。⏳ 该用法为设想，未实现。
5. **教学与实验室环境的可复现演示**：把"一段操作流程"变成可执行、可审计、可复现的脚本，配合逐步截图记录，用于演示与教学复盘。

## 9. 与 blog-my 的关系：知识 + 操作如何互补

`blog-my` 原本是一个多模型桌面聊天客户端，已经具备本项目最需要的三块地基：**多模型 LLM 网关**（`llm/`）、**用户与数据体系**（MySQL + GORM）、**桌面壳与页面**（Electron + templates）。两条新链在这个地基上生长：

| 能力 | 提供方 | 回答的问题 | 输出形态 |
|---|---|---|---|
| **知识**（RAG） | `rag/` + `web/kb.go` + MySQL | "这是什么 / 我的资料里怎么说的" | 带出处的文本回答（SSE 流式） |
| **操作**（CUA） | `cua/`（契约 `cua/1`） | "这件事在界面上怎么做" | 一步步的键鼠动作与执行回执 |

互补关系体现在三个层面：

1. **知识指导操作**：RAG 检索到的领域知识（业务规则、系统说明、历史处理记录）作为 CUA 的任务上下文，让模型知道"该填什么、该选哪个"，而不是对着界面瞎猜。🔶 设计如此
2. **操作沉淀知识**：CUA 每一步的截图、动作、结果本身就是过程档案，可以入库成为后续同类任务可检索的素材。🔶 设计如此
3. **共用一套基础设施**：同一个本地 Ollama 服务同时承载嵌入、视觉转写、生成三类模型；同一套用户体系让"谁的资料"与"谁在执行"可追溯；同一个 Go 后端承担接口层，Python 侧的 CUA 通过契约/HTTP 与之交互（🔶 具体接线方式待 `01-architecture.md` 定稿）。

一句话：**RAG 让助手知道自己该做什么，CUA 让助手真的做得出来；两者共享同一份本地数据与模型。**

## 12. 局限与伦理安全说明

### 12.1 能力局限（如实声明）

- **视觉操控比 API 慢且脆**：受分辨率、动画、渲染延迟、主题影响；本项目明确把它定位为最后手段。
- **图片检索上限取决于转写质量**：图片不产生向量，全靠视觉模型生成的"描述 + OCR"；转写漏掉的细节检索永远找不回来。这是当前方案最脆弱的一环 ⏳。
- **视觉链路"慢"是结构性代价（已实测）**：本地视觉模型**冷启动约 56.5 秒**（166 字节 8×8 PNG 直打 Ollama 实测 56491 ms），**热态一次图片转写约 13.3 秒**（前端上传到入库提示），单步推理 9–78 秒（契约 §8 第 4 条）。图片入库链路**已通过**端到端验收（见 11.1），但「慢」不会消失，只能靠分档预算与超时对齐兜住（来源 `../day23/notes.md` 第 133、157、189 行）。
- **无重排（rerank）**：只有余弦 topK，语义相近但无关的块可能混进上下文 🔶。
- **无权限硬隔离**：知识库 `user_id` 目前是归属标记，数据层未做多用户硬隔离 🔶，多用户部署前必须补齐。
- **本地文本模型不支持多模态回喂**：把原图作为多模态消息喂回生成模型的能力，受生成模型是否支持视觉输入限制 ⏳。
- **无系统级性能基准**：已有若干单点实测（VLM 冷启动 56.5 秒、图片转写热态 13.3 秒、单步推理 9–78 秒），但**没有**检索延迟与吞吐基准、也没有 CUA 任务成功率评测；容量推演仍只是 📐 估算 ⏳。
- **真实视觉操控闭环已端到端验证**（2026-10-11，Lead 实测 **28 步 done**，见 11.1）；但下列**未覆盖面**仍然存在 ⏳：「四级路由与 `E_STALL` / `E_LOOP` 的真实触发」需要真实多步轨迹**并在真实失败场景下**才可能触发（本轮 28 步 run 未触发）；多显示器 / 混合 DPI、弹窗按钮 OCR、单任务成功率与坐标命中率统计（`../verify/task-7-cua-contract-tests.md` 第六节）。
- **多显示器 / 混合 DPI 未实测**：本机为单屏，虚拟桌面合并坐标系的行为无法验证（`01-architecture.md` §13 R4）⏳。

### 12.2 转人工边界（必须由人接管）

以下环节**一律不允许 agent 自主决定**，检出即返回 `need_human` 并交还控制权：

1. **资金支付**：付款、下单、确认购买、转账；
2. **权限授权**：UAC 提权、系统权限授予、账号授权、证书安装；
3. **不可逆删除**：删除文件/记录、格式化、清空、重置、覆盖；
4. **法律与合规签署**：电子签名、合同确认、条款同意；
5. **身份验证**：验证码、密码输入、生物识别；
6. **语义不明**：模型无法判断按钮含义，或无法确认操作后果。

契约把这些定义为"**正确地交还控制权**"，而不是失败——转人工是设计的一部分，不是缺陷。

### 12.3 破坏性操作禁止自动化

- 弹窗/界面中若按钮文字命中**破坏性词表**（删除、卸载、格式化、清空、重置、覆盖、支付、付款、确认购买、允许、授权、安装、同意；Delete、Uninstall、Format、Erase、Reset、Overwrite、Pay、Purchase、Allow、Grant、Install、Agree），**不点击，直接转人工**。
- `risk=high` 的动作默认需要护栏放行；放行策略由调用方配置，协议层只负责标记。
- 危险组合键（含 `win` 的系统级组合、`alt+f4`、`ctrl+alt+delete`）默认关闭，需显式 allowlist 打开。
- 执行器不提供任意命令执行能力：`exec`/`shell`/删文件/关进程/注册表**不在动作协议内**，属于独立的**白名单**通道。一个能被截图内容影响的模型，不应该同时握着任意命令执行权。

### 12.4 用户安全与紧急停手

- `pyautogui.FAILSAFE = True` **永久开启**且不作为可配置项暴露给模型：把鼠标快速甩到屏幕左上角即可立即停手；
- 坐标越界一律拒绝（`E_OUT_OF_BOUNDS`），不 clamp、不取模、不翻转到另一块屏；
- 步数预算（默认 40）与墙钟预算**双重**约束，任一超限即终止；墙钟默认值**按后端分档**：云端 API 档 300 秒，本地 VLM 档 1800 秒（契约 §8 第 4 条 v1 裁定，2026-10-11）；
- 任何错误终止时**先释放所有仍按下的键**，避免系统留下"Ctrl 卡住"的状态；
- 每步之间强制间隔（≥150ms），防止把 UI 事件队列打爆产生更诡异的失败。

### 12.5 数据隐私与合规

- **本地优先**：嵌入、视觉转写、生成默认都在本机 Ollama 上运行，知识库内容与截图不出本机；不产生云端调用费，也不把私人文档发给第三方。
- **截图含隐私**：视觉操控必然读取屏幕内容，可能包含聊天记录、邮件、个人信息。使用前需由用户明确知情并授权，且截图只送本地模型、不落外发的日志（🔶 设计如此，落地需在实现中确认）。
- **可审计**：检索结果带出处（文档标题、块序号、是否图片）；每次能力路由记录级别与理由；执行有 `ActionResult` 回执。出问题时能定位到"哪一步、看了什么、做了什么"。
- **合规边界**：不用于绕过验证码、破解软件、批量注册、爬取受限数据、规避平台风控；自动化操作第三方软件时应遵守其服务条款与当地法律法规。

### 12.6 责任边界

本项目提供的是**执行工具**，不代替使用者作出业务判断。任何涉及资金、授权、删除、签署的操作都必须由人确认；使用者对自动化流程的实际后果负责。系统设计上通过"默认停手""破坏性词表""风险分级""双预算"四条机制，把"误操作的期望损失"压到低于"少做一步的代价"。
